# Spike 1.1: play bridge clock and input timing

**Question:** can a `--script` main loop run an unmodified Godot game, freeze it between agent
commands, step exact frames, and inject input that the game sees exactly like a real key press,
deterministically?

**Answer: yes.** Code: `addons/ghostlap/play/bridge.gd`, `cli/src/ghostlap/play/bridge_client.py`.
Tests: `cli/tests/test_bridge.py`, with fixture `cli/tests/fixtures/bridge_probe/`.

Measured on Godot 4.7.2, Linux, headless. CI also runs the tests on 4.3.

## Findings

| # | Finding | Decision |
|---|---|---|
| 1 | Blocking in a node callback freezes the whole game: no physics, `_process`, timers or tweens advance. A `look` after 0.5 s of real time returns the identical frame and hash | Block at the end of each frame, serving the socket |
| 2 | **The v1 runner's input path is wrong for `_process` code.** With `Input.action_press()` called from a callback at the end of frame f−1, `is_action_just_pressed()` is true on frame f in `_physics_process`, but **never** in `_process`. `_input` also gets the pushed event one frame early | Inject everything with **`Input.parse_input_event()`** and no manual flush. Godot buffers it and flushes at the start of the next iteration (input buffering is on even headless), so on frame f `_input`, `_physics_process` and `_process` all see it once, like a real key. Verified for actions, raw keys (`Input.is_key_pressed`) and mouse buttons |
| 3 | Calling `Input.flush_buffered_events()` right away, or also `push_input`, delivers events a frame early or twice | Never flush or push manually |
| 4 | Physics callbacks still run every iteration at `Engine.time_scale = 0` (with delta 0) and while the tree is paused (for `PROCESS_MODE_ALWAYS` nodes). Hitstop doesn't stall the clock in either callback | Block in `_process` anyway: it runs once per iteration regardless of the game's tick rate |
| 5 | Frame 0 is the end of the iteration in which `change_scene_to_file()`'s scene became current (Engine process frame 1 here). The scene's `_ready` has run, plus one physics tick | Frame f ↔ engine iteration `it0 + f`; `it0` is reported in `look` |
| 6 | `reload_current_scene()` from game code works: the start scene really is `current_scene` | Use `change_scene_to_file`, not the v1 runner's `add_child` |
| 7 | **The headless root viewport is 64×64.** GUI clicks at normal coordinates miss, and anchored UI is laid out for 64×64 | The bridge sets `root.size` to the project's viewport size in headless mode, so layout and clicks match a rendered run |
| 8 | `Expression` can't reach engine singletons (`Input`, `Engine` …). Built-in function names shadow members: a property called `log` fails to parse (`log()` is a built-in) | Pass singletons as named inputs. Document the shadowing; `node('…').get('log')` works |
| 9 | Determinism: the same inputs give identical per-frame state hashes as one 240-frame step, 7-frame steps with real-time sleeps, or single-frame steps. On all 6 examples (2D and 3D, 600 frames of seeded random input), whole vs 13-frame chunks were identical with no engine errors. A different `seed` diverges at frame 0 | Determinism holds on one machine and version. Cross-machine replay is still unverified (phase 2) |
| 10 | Overhead: 240 single-frame round trips plus Godot startup ≈ 1 s; a 600-frame chunked session ≈ 1.8 s including boot | Fine for interactive use |

## Not covered (moved to 1.2)

- Window mode: whether a blocked window shows "not responding", and whether `DisplayServer.process_events()` in the wait loop is safe. This needs a display or xvfb. xvfb isn't installed locally, and opening windows on the dev desktop was avoided.
- Screenshots of the frozen frame via `RenderingServer.force_draw()`.

## Follow-up for the feel toolkit

Finding 2 also affects `addons/ghostlap/probe/runner.gd`: feel probes would miss jumps in games that read `is_action_just_pressed` in `_process`. The examples read input in `_physics_process`, so the existing tests don't catch it. Port the runner to `parse_input_event` as well.
